## 三、服务间依赖关系与断电重启风险点

```
nginx ──┬─ /certagent/ ─→ certagent (127.0.0.1:8125)
        └─ /craw/     ─→ certverify (127.0.0.1:8758) ─弱依赖→ decryptor (0.0.0.0:8500)
```

风险点：
1. **certverify 断电后起不来**（已修复）：systemd 默认 `StartLimitBurst=5`+`StartLimitIntervalSec=10s`，断电后若解密服务/网络/代理未就绪，主进程连挂 5 次停止恢复 → 永久 `failed`。修复见第四章。
2. **decryptor 先于 certverify** 的软依赖：certverify 用 Wants（弱依赖），decryptor 挂了只影响"加密文件上传"，网页本体可服务，不会连锁 failed。
3. **nginx 与后端顺序**：nginx 常先起，后端起 502 属暂态，业务后端 `Restart=on-failure` 会自恢复。

## 四、2026-09-24 已实施的重启保护（certverify）

改动集中在 `crawl4ai-main/Linux/deploy/`：

| 机制 | 配置 | 作用 |
|---|---|---|
| 启动前依赖探测 | `ExecStartPre` → `cert_verify_ready.sh`（新增） | 依次等路由(≤60s) → 解密服务8500(≤60s) → `CERT_PROXY`代理(≤60s)；任一超时只告警、**永远 `exit 0`**，不制造启动失败 |
| 崩溃自动恢复 | `Restart=on-failure` + `RestartSec=5` | 主进程崩溃后 5 秒重试 |
| 无限次启动尝试 | `StartLimitIntervalSec=0` | 关闭默认「10s 内失败 5 次即永久失败」，断电也能等依赖到位再拉起 |
| 弱依赖 | `After=`/`Wants=decryptor.service` | 解密服务缺失不连锁 failed |
| 探测时间放宽 | `TimeoutStartSec=240` | ExecStartPre 最坏约 182s，默认 90s 会误杀 |

验证命令（已在`服务器部署清单.md`第 11 章）：
```bash
# 更新服务器：部署到服务器后再执行
curl -s http://127.0.0.1:8758/
systemctl is-active certverify        # 期望 active
journalctl -u certverify -b            # 断电后本次启动无 StartLimit 报错
systemctl show certverify -p NRestarts
```

> ⚠️ 此改动尚需在服务器上 `cp` 新 unit + `daemon-reload` + `systemctl restart certverify` 生效（本机未直连，未执行线上部署）。
