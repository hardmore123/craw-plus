## 5. 安装定时任务

采集分两步走，不要都放进定时任务：

| 步骤 | 场景 | 频率 | 说明 |
|---|---|---|---|
| 商品发现 | `search`（S1） | 低频 / 手动 | 关键词搜索，把商品收进库 |
| 价格监控 | `monitor --from-db`（S2b） | 每天（timer） | 按已入库 SKU 快照价格 |

为什么定时任务用 `--from-db` 而不是按型号搜索：SKU 是站内唯一标识，不会误匹配。

按型号搜索会把配件价格记成整机价格 —— 框架已做型号校验会拒绝入库，但白跑了请求。

## 7. 故障排查顺序

按这个顺序查，不要跳步。

1. **浏览器起不来** → 检查 `OVERSEAS_BROWSER_EXECUTABLE` 路径与可执行权限；
   `chrome` 和 `chrome_crashpad_handler` 都要 `chmod 755`；缺库跑 `install-deps`。
2. **页面超时 / 不可连** → 服务器出网问题，配 `OVERSEAS_PROXY`；
   用 `timeout 12 bash -c "</dev/tcp/www.amazon.ca/443"` 快速判断。
3. **`blocked=true`** → 被反爬。降低频率（加大 `OVERSEAS_MIN_INTERVAL`）、
   错峰执行；`crawl_error` 表里 `kind=blocked` 的比例是关键指标。
4. **字段为空** → DOM 改版。跑 `probe` 定位坏掉的选择器，改对应
   `sites/<code>/schema.json` 的 `selectors` 兜底链，**不需要改 Python 代码**。
5. **中文乱码** → `overseas.env` 里确认 `LANG=C.UTF-8`（systemd 下 LANG 默认为空）。

## 8. 迁移到 PostgreSQL（后续）

当前是 SQLite（`data/overseas.db`）。表结构已尽量用标准 SQL，
SQL 全部收在 `overseas/db.py` 一个文件里，迁移时只替换该文件即可，
上层场景与抽取逻辑不用动。触发迁移的信号：多机并发采集、单表超千万行、需要并发写入。

## 9. 安全与合规要求

- `overseas.env`（含代理地址）、`models.txt`（业务型号）、`data/` 不提交 Git。
- 抓取间隔不要为了快而调到 1~2 秒，容易触发风控并影响目标站点。
- Amazon 等站点 ToS 禁止未授权抓取；用于竞品调研前请完成内部确认，
  或改用官方/第三方数据源。

## 12. SPEC 故障排查

1. 先看 `crawl_run` / `crawl_error` 和 systemd journal，确认是网络、浏览器、404 还是解析失败。
2. 检查 `python -m overseas.cli sites --json` 是否仍能发现六个 `*_jp` 适配器。
3. 目标页能访问但中文覆盖下降时运行 `python -m overseas.cli spec-dict`，补充 `overseas/dict/spec_ja_zh.json` 后执行 `scripts/refresh_spec.py --export-only`。
4. 站点页面重或超时时提高 `OVERSEAS_NAV_TIMEOUT`，不要把抓取间隔降到 1~2 秒。
5. PowerShell 下运行 `check_xlsx.py` 建议先设置 `$env:PYTHONIOENCODING='utf-8'`，避免日文样例受 GBK 控制台编码影响。

## 14. SPEC 定时任务失败时读取系列状态

SPEC 定时任务的退出码只回答“本轮是否完整成功”，不能代替系列级审计。`scripts/refresh_spec.py` 每轮会在输出目录自动生成：

```text
SPEC_系列状态_YYYYMMDD.csv
SPEC_系列状态_YYYYMMDD.xlsx
SPEC_系列状态_YYYYMMDD.json
```

文件列出每个品牌/系列的最新 `success`、`empty` 或 `failed`，并保留请求 URL、实际 URL、尝试 URL、型号计数、规格行数、错误类型和消息。任务返回非零时，先保存该状态文件，再按以下顺序定位：

```bash
cd /home/hisense/pro/overseas
venv/bin/python -c "import sqlite3; c=sqlite3.connect('data/overseas.db'); print(*c.execute('SELECT run_id,brand,series,captured_week,status,status_source,model_expected,model_ok,model_empty,model_failed,row_count,error_kind,message,finished_at FROM spec_series_status ORDER BY id DESC LIMIT 100'), sep='\\n'); c.close()"
venv/bin/python -c "import sqlite3; c=sqlite3.connect('data/overseas.db'); print(*c.execute(\"SELECT run_id,url,stage,kind,message,created_at FROM crawl_error WHERE stage='entry' ORDER BY id DESC LIMIT 50\"), sep='\\n'); c.close()"
```

判定方式：

- `success`：至少一个型号且至少一行规格；
- `empty`：请求本身成功但没有可用 table/型号/JSON/规格行；
- `failed`：HTTP 404/其它 HTTP 错误、超时、浏览器/网络异常或解析异常；多型号系列部分失败也属于 `failed`。

单个系列的 `empty/failed` 不应让其它系列静默消失。先保留状态文件和数据库，再针对品牌/系列补采；不要把空系列写成伪造型号，也不要用旧 Excel 覆盖本轮失败结果。入口页 `list_series` 或多级 `series_entries` 为空时没有可安全落入的系列行，程序会写 `crawl_error(stage=entry, kind=empty)` 并把 `crawl_run.status` 设为 `failed`，此时必须查看 `crawl_error`。

Linux 示例补采：

```bash
venv/bin/python -m overseas.cli --db data/overseas.db spec-crawl --site sharp_jp --series X7A
venv/bin/python scripts/export_spec_status.py --db data/overseas.db --site sharp_jp --format all --out "data/SPEC_夏普状态_$(date +%Y%m%d)"
```

升级到带状态表的代码后，先执行一次 `init-db`。旧库只有 `spec_series` 而没有状态历史时，状态导出会明确写 `status=success,status_source=legacy`；这只是兼容性回溯，不代表本周访问结果，不能据此跳过本周验收。
