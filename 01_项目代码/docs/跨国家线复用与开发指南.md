## 1. 两种线型：日本线 vs 北美线（决定复用方式）

新开一条线前，先判定它属于哪一种数据源结构，这决定了要复用哪套采集路径。

### 1.1 日本型（单一聚合价格/评论站）

- **SPEC**：每个品牌一个官网站点，`SPEC 站点 code == 品牌 code`（`hisense_jp` 既是品牌又是官网）。
- **价格 + 网评**：全部品牌统一走**一个聚合站**（`価格.com` / `kakaku_jp`），按型号搜索即可拿到跨店铺价格与用户评价。
- 优点：价格/网评只需一个适配器；缺点：依赖聚合站的收录。

### 1.2 北美型（多零售站分散）（ca / us / mx）

- **SPEC**：同样每品牌一个官网站点（`hisense_ca` 等）。
- **价格 + 网评**：**没有聚合站**，分散在多个零售站（Amazon / Best Buy / Walmart / Costco …）。品牌与零售站是**多对多**：同一型号要在每个启用的零售站各搜一次，价格与评价在**同一商品页同步抽取**（`parse_product`）。
- 关键复用点：`overseas/retail_common.py` 的 JSON-LD 通用抽取，让多数零售站几乎零成本接入。

> 判定方法：先花半天调研目标国家「有没有一个像 kakaku 那样的比价/聚合站」。有→走日本型（省一大半事）；没有→走北美型（用零售站 + JSON-LD）。

## 2. 可复用资产清单（哪些不用动）

以下模块**跨线通用，新开线原则上不改**。位置均在 `overseas/`。

### 2.1 框架内核（零改动）

| 文件 | 职责 | 为什么通用 |
|---|---|---|
| `config.py` | 全部 `OVERSEAS_*` 环境变量（路径/限速/浏览器/代理/缓存/翻译/熔断超时） | 配置与站点无关 |
| `models.py` | 领域模型：`Product` `Review` `PriceSnapshot` `ReviewSummary` `SpecSheet` `SpecRow` `ProductPayload` `SearchHit` | 数据结构与国家无关 |

| `infra.py` | `RateLimiter`（按域名+状态码退避）/ `BlockDetector`（反爬识别）/ `DiskCache` / 代理探活 | 反爬与限速逻辑与站点无关 |
| `fetchers.py` | `HttpFetcher`(urllib) / `BrowserFetcher`(Playwright) + 统一 `Dom` 接口；入口滚动稳定、`eval_js`、按页面类型可调等待 | 抓取能力通用 |
| `extract.py` | 声明式抽取引擎：按 `schema.json` 的选择器/正则/JSON-LD 取值 + transforms | DOM 改版只改 JSON |

## 3. 每条新线真正要写的东西（哪些必须新写）

### 3.1 一条 `regions_config.Region`（数据声明，非代码逻辑）

在 `overseas/regions_config.py` 加一个 `Region`，声明：品牌清单、每品牌的 SPEC 官网站点、价格/网评零售站（北美型）或聚合站（日本型）。`enabled` 初始置 `False`，逐站验证通过后再开。参照现有 `_CA` / `_US` / `_MX`。

### 3.2 SPEC 站点适配器（每品牌一个）

目录：`sites/<code>/{__init__.py, adapter.py, schema.json?}`。继承 `SiteAdapter`，实现：

- 单级站点（一系列一页）：`spec_entry_url()` + `list_series()` + `parse_spec()`。
- 多级站点（入口→系列→多型号页，如松下/大部分北美站）：`series_entries(open_dom)` + `parse_spec_model()` + `model_from_url()`。
- 声明能力：`supports_spec = True`；设 `country` / `channel`（导出列用）、`protection`、`suggested_interval`、入口等待/滚动配置。

字段抽取尽量交给 `schema.json`（选择器写 JSON）或 `spec_parser.py` 通用解析器，保持适配器代码薄。

### 3.3 零售站适配器（北美型，每零售站一个）

目录同上。实现：

- `supports_retail = True`；
- `find_product(dom, html, model, query)`：从搜索结果**严格按型号匹配**挑商品（宁缺毋滥，基类已给默认实现）；
- `parse_product(dom, sku, url)`：同一商品页同步抽价格 + 评分聚合 + 评价，返回 `ProductPayload`。**多数零售站直接调 `retail_common.jsonld_product_payload(...)` 即可**，再按需用站点 CSS 补充。

Amazon 类站点走 CSS（无稳定 JSON-LD）；其余零售站优先 JSON-LD。

### 3.4 词典（仅需中文列的线）

日本线需要 `dict/spec_ja_zh.json`（日→中）。英文站（北美/欧洲）**不强制中文 100% 覆盖**，`--region` 非 jp 时刷新脚本已跳过中文校验；如需中文，另建对应词典或接翻译接口。

## 4. 标准开发流程（从零到交付）

固定 Python（本机）：`C:\Users\likunyuan\AppData\Local\Programs\Python\Python312\python.exe`（装了 Playwright，Edge channel=msedge）。所有采集/浏览器命令用它。

### 步骤 1 · 线型判定与配置声明
- 调研目标国家有无聚合价格站 → 判定日本型 / 北美型。
- 在 `regions_config.py` 加 `Region`（品牌 / SPEC 站点 / 零售站或聚合站），`enabled=False`。

### 步骤 2 · 入口发现（只读，先不入库）
- 用 `_probe_spec.py`（或等价探测）逐站访问官方 TV 入口，**只做只读诊断，不写正式库**。
- 目标：确认每个品牌官网**当前实际的系列数/型号数**，并定位入口发现的技术难点（懒加载、分页、接口、多尺寸 swatch）。
- 验收：入口发现数量稳定（连续 2–3 次运行无抖动），与官网可见数量一致。**参考值只作对照，实际以审计为准，不可用参考数字硬凑。**

### 步骤 3 · SPEC 采集与解析
- 为每品牌写/调适配器，单站真实页面验证一个代表型号解析出的规格行数合理。
- 全量采集：`spec-crawl --site <code>`（重站设 `OVERSEAS_NAV_TIMEOUT=60`）。
- 导出：`spec-export` 或 `refresh_spec.py --region <r>`。
- 验收：`crawl_run=completed`；系列状态 success/empty/failed 分类正确；空/失败**不静默**，落审计；Excel 有表头/型号列/规格行。

### 步骤 4 · 型号汇总（价格/网评线输入）
- `export_spec_models.py --region <r>` → `SPEC_型号汇总_<region>.csv/xlsx/json`。这是价格线和网评线的唯一输入清单。

### 步骤 5 · 价格 + 网评
- 日本型：`crawl_kakaku_prices.py` / `crawl_kakaku_reviews.py`（参数换品牌/型号清单）。
- 北美型：`crawl_ca_retail.py`（读型号汇总，每启用零售站 search→find→parse，产价格表 + 网评表）。强防护站先 `enabled=False`，低频小样本验证通过再逐个开。
- 验收：状态计数守恒（`ok + no_item + no_price + no_reviews + not_target_year + failed + skipped_* == 输入型号数`）；CSV 行数与库统计一致；无 `blocked`。

### 步骤 6 · 入库（供后端）
- 采集脚本加 `--save-db --db data/<库>`；或已抓 CSV 用 `import_kakaku_files.py`（日本型）秒级灌库。
- 升级 schema 前**先备份** `data/backup/`。

### 步骤 7 · API / 前端 / 定时
- `regions_config` 对应 `enabled=True`（或 `api/regions.py`），前端自动出现该地区。
- 通道验证（`/api/probe`）先探再抓；补该线的价格/网评 systemd 定时单元。

### 步骤 8 · 交付
- `pack.py` 打代码包（排除 `data/`、DB、缓存、浏览器目录、真实 env、结果 Excel/CSV）。
- 数据/验收包单独打（如 `overseas-spec-<region>-data_*.zip`），带 manifest + SHA256，标 CONDITIONAL/FINAL。

## 5. 注意事项与红线（每条线都要遵守）

以下是三线实战沉淀的教训，**违反任一条都可能导致数据错误或被封**。

### 5.1 反爬 / 限速（安全边界，不可为提速牺牲）
- **不放宽域名级限速换速度**：`OVERSEAS_MIN_INTERVAL`（默认 6s）与站点 `suggested_interval`（kakaku 7s）是被反爬约束的边界；拦截后的退避与重试代价远高于省下的等待。
- **不并发写同一个 SQLite**：会写锁竞争 + 审计交叉污染。要并发抓取必须**共享同一 `RateLimiter`** + **单写线程/队列**，并发度 2–3 起步，先小样看 `blocked` 比例。
- **不要把业务锚点当 `wait_selector`**：翻页到尽头本就无内容，会被 `BlockDetector` 误判 `no_anchor_element` 中断整个型号。真拦截靠状态码(403/429/503)/验证码关键字/正文过短三路识别。
- **HTTP 404 优先于 blocked 判断**：404 是正常缺页（回退/跳过），不重试、不计入熔断，不能因 404 页正文短误记为拦截。

### 5.2 匹配 / 链接（数据正确性）
- **型号匹配四级优先**：`以型号开头 > 独立词 > 子串 > 兜底`，纯子串会命中旧机型/配件（搜 `50A6S` 曾命中 2012 年 `DCB-IP50A6SVP`）。零售站 `find_product` 宁缺毋滥，找不到返回 None，绝不盲取第一个（否则价格/评价张冠李戴）。
- **相对链接必须补成绝对 URL**，否则 `goto` 静默失败（`status=-1`）还不报错（kakaku 讨论主题相对路径踩过）。

### 5.3 入口发现（完整性，北美线重灾区）
- **多尺寸别只抓代表尺寸**：一个系列常有多个尺寸型号，DOM 默认只渲染一个代表。要抓全尺寸，用权威来源：Hisense swatch `data-product`、Samsung 官方 finder 接口、Sony OCC 详情 `baseOptions`、Philips 前端分页逐页点击、LG 详情页同系列尺寸展开。
- **懒加载要等稳定**：入口首个链接出现≠全部注入。用 `spec_entry_scroll_until_stable` 等到目标集合稳定（连续 N 轮不增长）再取，REGZA 曾因时序只发现 1 个系列。
- **参考值只作对照**：官网实际数量随上下架变化，以审计为准；**不能用参考数字伪造补齐**（Philips 参考 25 实际不同口径、Samsung 接口 64 才是权威）。

### 5.4 空 / 失败 / 覆盖度（诚实审计）
- **空/失败不得静默**：`empty`（请求成功但无数据）与 `failed`（404/超时/解析异常）必须落审计（`spec_series_status` / `kakaku_task_status` / `retail_task_status`），**不能用空表覆盖旧快照**。
- **"抓得少" ≠ "漏抓"**：先实测核对（如新机确实 0 评价、TCL 老系列 JSON 确 404），再判断是否 bug。缺口要分类：`no_item`（站点无此商品页）/ `not_target_year` / `no_reviews`（新机暂无评价）各有含义。
- **退出码 0 不能作为采集成功判据**：曾因脚本缺 `if __name__ == "__main__"` 入口而「1 秒退出码 0 但零产出」。必须同时核对 `crawl_run` 状态、状态表行数、导出文件行数。

### 5.5 导出 / 数据 / 库（不丢数据）
- **先写 CSV 再写 XLSX**：XLSX 常被 Excel 占用导致 `PermissionError`，先写 XLSX 会连 CSV 一起丢；占用时自动改写带时间戳文件。
- **改词典/翻译免重抓**：导出优先用库里 `item_zh`（旧翻译），**光改词典不生效**，用 `retranslate_spec.py` 回写库或 `refresh_spec.py --export-only`。日本线还需注意「翻译撞车」先证伪（脚本读真实文件）再改，Excel 拖拽填充柄的递增不是爬虫问题。
- **schema 升级先备份**：`data/backup/` 用 SQLite `Connection.backup()` 做一致性快照；`-wal/-shm` 是在线写配套文件，API 运行期间不要手工删或只复制主库。
- **不同语义不得误合并**：SPEC 主行名归一（`canonical_item_ja` / `_norm_item_ja`）要保留区分性内容——mm vs kg、2012 vs 2026 基准、不同用途 USB 端子绝不合并，否则丢数据。
- **审计记录只增不改**：不删历史 `running`/`run_id` 记录来「让统计变好看」。

### 5.6 长任务 / 进程 / 缓存
- 长任务（SPEC 全量数十分钟、kakaku 单品牌 15–25 分钟、REGZA ~80 分钟）用后台进程跑；`Tee-Object`/`Out-File` 缓冲到进程结束才落盘，轮询期间读不到中间日志属正常，判断进度用进程状态 + 产物文件。
- 正式周度快照**不依赖缓存**（`--page-cache` 默认关），缓存命中要如实标记，避免把过期价格/发售日写进快照。
- 每次实测后**清理临时探测脚本**（`_probe_*.py` / `_chk.py` / `_*.log`），避免污染交付目录。`pack.py` 排除规则用精确前缀（曾因 `_*.py` 误删所有 `__init__.py`）。

### 5.7 环境 / 部署
- 服务器常访问不了 Playwright CDN，用离线 Chrome：`OVERSEAS_BROWSER_EXECUTABLE=/opt/chrome-linux64/chrome`；Linux 无头必须 `--no-sandbox`（否则静默卡死，已在 `BROWSER_ARGS` 预置）。
- PowerShell 默认 GBK，校验脚本打印日文/多语言样例前设 `$env:PYTHONIOENCODING='utf-8'`。
- **服务器出海线路是海外零售站采集的硬阻塞**：实测部分站点被 IP 层 403 或超时。规模化前必须先解决代理/专线，并用 `/api/probe` 通道验证「先探再抓」。
- 合规：运行前确认目标站 ToS、访问频率、代理使用与数据用途；不同站点分别遵循各自规则。
