## 3. 必须知道的实测结论（决定预期，别抱错希望）

### 3.1 网评有**站点硬上限**，不是抓取能力问题

| 站点 | 每型号可取 | 证据 |
|---|---|---|
| amazon_ca | **14~50 条** | 19 评分→14 条；87 评分→34 条；有达 50 条上限的 |
| **amazon_us** | **8 条（硬顶）** ❌ | **总评分 2,742 的产品也只给 8 条**；总评分 10/42 也是 8 条 |
| amazon_mx | 2~5 条 | 总评分 12→5 条；总评分 4→2 条 |

**US 已穷尽 9 种途径均无效**：`pageNumber`、`sortBy`、`filterByStar`、
`/hz/reviews-render/ajax/reviews/get/`（403）、`/portal/customer-reviews/`（跳登录）、
`ref=`、`#customerReviews`、`opt=1`、带/不带 `reviewerType`。

→ **US 网评总量上限 ≈ 405 × 8 ≈ 3,240 条**。这是服务端策略，**不要在这上面浪费时间**。

### 3.2 品牌搜索池命中率低（这决定为什么逐型号搜索不可省）

| 站点 | 池页数 | 候选数 | 型号命中率 |
|---|---|---|---|
| US | 1 | 17 | **6.7%** |
| US | 8 | 140 | **19.0%** |
| CA | 8 | 304 | **22.1%** |

Amazon 品牌搜索受**相关性排序**限制，8 页也只覆盖 ~20% 型号。
故配置为：**池优先（省 1 次搜索）+ 池内未命中回退逐型号搜索**。

### 3.3 并行**不建议**

实测对比（同批模型）：

| 方案 | 耗时 | 结论 |
|---|---|---|
| 串行 | ~7.3 min / 9 型号 | 基准 |
| 三站并发 | 11.2 min | **反而更慢**（CPU/代理争抢） |
| 同站拆 2 进程 | 失败 | **profile 被锁** → 降级临时上下文 |

且 `RateLimiter` 是**进程内**的，并发 = 同一出口 IP 速率 ×3 → 封禁风险显著上升。
**结论：串行比并行更快且更安全。**

### 3.4 默认配置就是最优

三站已调好，**不要为了"更快"随意改**：

```json
"search":   { "batch": { "prefer_pool": true, "search_pages": 1,
                         "fallback_per_model": true, "max_candidates": 60 } }
"paginate": { "reviews": { "type": "filter_sweep", "max_reviews": 50,
                           "first_screen_cap": 8 /* 仅 us */ } }
"fetch":    { "interval_sec": 8.0 }
```

## 7. 故障排查

| 症状 | 原因 | 处理 |
|---|---|---|
| `命中登录墙（会话失效/未登录）` | state 过期 | 重跑 §2.1 的 `login` 命令（**必须加 `--profile`**） |
| `持久化 profile 打开失败…回退临时上下文` | 同站已有进程占用 profile | **确认同站只跑一个进程**；杀掉残留 msedge |
| 大量 `blocked`（>5/站） | 出口 IP 被限流 | 停 30~60 分钟；或把 `interval_sec` 从 8 提到 20 |
| `no_price` 比例异常高 | 正常（无 buybox）或价格区校验过严 | 抽 2~3 个型号手工看页面有无主价 |
| 价格数量级明显不对（如 $9.49 买电视） | 配件价 / 变体价 | 见 §2.2 第 5、6 项；已修，若复现请记录 ASIN |
| 进程无输出且 CPU 极低 | 卡在浏览器导航 | 检查代理连通；kill 后重跑（幂等） |
| 前台命令超时（~10min） | 执行器上限 | **改用后台任务** |

**幂等性说明**：重复跑同一站是安全的 —— `price_snapshot` 只增快照、
`review` 有 `(product_id, review_key)` 唯一约束、`crawl_run` 会新增一条审计。
`reviews_new=0` 表示"已抓过"，不是失败。
