# 任务表与验收标准

> 版本：v1.0（2026-09-16）
> 用途：排期与验收。**每条任务的"完成定义"都必须是可执行验证的命令或可核对的数字**，
> 不接受"已实现""基本可用"这类描述。
> 关联：`现阶段技术方案与效果指标.md`（指标定义）、`AdapterSpec_schema规范.md`（契约）

---

## 0. 通用验收规则（所有任务都适用）

### 0.1 三条硬门槛

任何任务声明完成前，必须全过：

| 门槛 | 验证命令 | 判据 |
|---|---|---|
| **代码可编译** | `py -3.12 -m py_compile <改动的每个 .py>` | exit 0 |
| **回归不破坏** | 见 §0.2 回归基线 | 四站数字全部不变 |
| **文档已同步** | 人工核对 | 改了白名单常量必须同步 schema 规范 §6 与 playbook |

### 0.2 回归基线（改动引擎/探测器后必跑）

```powershell
$env:OVERSEAS_DB = "data/sandbox_regression.db"
py -3.12 -m overseas.cli spec-crawl --site philips_ca
```

| 站点 | 期望结果 | 说明 |
|---|---|---|
| Philips CA | 系列 11，型号 25，终态 stable，ok=11 fail=0 | 分页站代表，必跑 |
| REGZA JP | 39 系列 39 型号 | 懒加载代表 |
| 秘鲁 Hisense | 13 系列 36 型号 | 静态列全代表 |
| Sony BRAVIA JP | 8 型号，且 schema 中**无** `discover.paginate` | 假分页信号代表 |

> 任何一站数字变化即视为回归失败，必须先解释原因再决定是否接受。

### 0.3 禁止事项（出现即验收不通过）

- 放宽或删除 `expected.model_count` 让找全率闸门失效
- 把 `link_selector` 改宽泛来凑数量
- 新增引擎不认的 schema 字段
- `cases.jsonl` 里标 `success` 但找全率 < 95%

## 第一部分：P0 覆盖面任务（决定能自动化多少站）

### P0-1 多级发现（总览 → 系列 → 型号）

**为什么优先**：当前最大能力缺口，且松下/夏普两站已有手写适配器可做对照。

| 参考实现 | `overseas/sites/panasonic_jp/adapter.py` 的 `series_entries()` |
| 预估 | 引擎 2~3 天 + 两站验证 1 天 |

**拆解**

| # | 子任务 | 完成定义 |
|---|---|---|
| 1.1 | Probe 能识别多级站 | `probe.py --entry <松下入口>` 输出中含多级判定标记；对 4 个已验证单层站仍判单层（不误报） |
| 1.2 | 引擎实现 `dom_anchor_two_level` | `generic_spec.py` 加分支；单元验证：给定两级 schema 能返回 `[(系列, [型号URL...])]` |

| 1.5 | 夏普端到端 | 同上 |
| 1.6 | 回归 | §0.2 四站基线不变 |

**验收标准**

```
✓ 松下：generic_spec 引擎抓到的型号集合 == 手写适配器抓到的型号集合
✓ 夏普：同上
✓ 找全率 ≥ 95%（对比官网标称数）
✓ 守恒：发现型号数 == 落库型号数
✓ 规格质量：抽 3 个型号，每个 ≥ 8 行规格且键值非空
✓ 四站回归基线不变
✓ playbook/multilevel.md 已含可用 schema 模板（非占位）
```

**指标提升**：L2 全自动站 4→6，结构型 4→5，P0 缺口 3→2

## 第二部分：P1 生产化任务（决定能否无人值守）

### P1-1 adapter_spec / onboard_run 库表

**为什么需要**：当前 schema 存 JSON 文件，没有版本、没有失败留档，
改版重生成和回滚都做不了。

| # | 子任务 | 完成定义 |
|---|---|---|
| 4.1 | 建表 | `schema.sql` 加两表（结构见技术方案 §6）；`db.init_schema()` 能创建 |
| 4.2 | schema 落库 | onboard 完成后 schema 写入 `adapter_spec`，同 code 版本号递增 |
| 4.3 | 每轮过程留档 | 每个 phase（probe/generate/run/verify/repair）写一条 `onboard_run` |
| 4.4 | 版本回滚可用 | 能按 `(code, version)` 取出历史 schema 并执行 |
| 4.5 | 兼容现有 JSON | `spec-crawl --schema <file>` 路径保持可用，不强制迁移 |

**验收标准**

```
✓ 跑一次 onboard 后，adapter_spec 表有 1 条记录、onboard_run 有 ≥5 条（每 phase 一条）
✓ 同站再跑一次，version 递增为 2，旧版本仍可查
✓ 能用 version=1 的 schema 成功抓取（回滚验证）
✓ 现有 --schema 文件路径不受影响
```

**指标提升**：L4 schema 持久化率 0% → 100%；失败现场留档率 → 100%

| 观察项 | 期望趋势 |
|---|---|
| 首轮通过率 | 随案例库增长而上升（目标 ≥ 50%） |
| 平均修复轮次 | 下降（目标 ≤ 3） |
| Step 0 命中相似站的比例 | 上升（说明案例库在起作用） |
| 单站接入耗时 | 下降（目标 ≤ 2 小时） |

## 排期建议

```
第 1 阶段（约 1 周）  P0-1 多级发现          → 全自动站 4→6
第 2 阶段（约 1.5 周）P0-2 xhr_api           → 全自动站 6→9，守恒率强验证
第 3 阶段（约 3 天）  P0-3 query_param       → 全自动站 9→10，自动化率达 60%
─────────────── 覆盖面目标达成，转生产化 ───────────────
第 4 阶段（约 1 周）  P1-1 库表 + P1-3 L3    → L1 补齐红线，L4 持久化
第 5 阶段（约 4 天）  P1-2 spec-health       → 获得改版自愈能力
第 6 阶段（约 3 天）  P2-1 合规 + P2-2 稳健  → 可对外交付
```

**先做 P0 的理由**：L4 生产化能力再完善，如果只覆盖 4 个站，业务价值有限；
而覆盖面上去之后，生产化的收益才被放大。唯一例外是 **P1-3（L3 规格质量）**——
它是 L1 红线，如果发现规格质量有系统性问题，会推翻已完成站点的验收结论，
所以**建议插到 P0-1 之后立刻做**。
