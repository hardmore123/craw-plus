# SPEC、评价抓取与任务生命周期的可靠性审阅

当前实现已经把请求分成确定性失败和瞬时失败，并加入有限重试、SPEC 候选 URL 回退、重复页检测、连续型号/系列熔断以及数据库审计；Kakaku 评价也设计了 レビュー → クチコミ 的回退链路。基于目录中实际代码的调用链，仍有路径会把部分成功误报为完整成功、覆盖已有 SPEC 数据，或让 API 查询的数据库与采集进程使用不同文件。硬超时和取消还会在子进程没有机会执行 `finish_run` 时留下永久 `running`，并且 Windows/刷新脚本的树终止并不可靠。目标目录没有 `.git` 元数据，无法用基线 diff 证明这些问题是否由本轮引入；以下结论均以当前文件和可复现的行为为依据。

**Watch for:** **P0 / confirmed** 多型号 SPEC 的 partial 写入会缩短 `spec_series.models` 并覆盖同周 `values_json`，导致原本成功的型号从导出/API 消失；**P1 / confirmed** 评价分页在已有一页数据后遇到瞬时失败会返回 `ok`、跳过クチコミ回退且不写失败审计；**P1 / confirmed** API 使用自定义 `--db` 时，任务子进程仍写 `config.DB_PATH`（`spec_refresh` 甚至不传 DB），而硬超时/取消不会闭合对应 `crawl_run`。

**Verdict**: NEEDS_CHANGES

## High-level view

多级 SPEC 的 404 候选回退、有限重试和连续系列熔断没有覆盖 partial 写入语义：当前实现仍会把不完整 `SpecSheet` 当成规范数据，替换模型列和值（confirmed）。评价抓取的 URL/指纹去重边界清楚，但已有一页数据不等于遍历完成，后续页故障会被当成成功（confirmed）。

API 查询使用服务启动时的 `SETTINGS["db"]`，任务构造器使用导入时的 `config.DB_PATH`；自定义 `--db` 会使任务写入另一份 SQLite（confirmed）。硬杀采集进程不会闭合其 `crawl_run`，而当前树终止路径不能保证清理浏览器子进程（confirmed）。

S4 详情页回退失败和 interval 调度失败都可静默发生：前者完成运行但不记错误，后者首次触发后可能重复入队，重启后又失去下一次触发时间（confirmed）。SPEC CLI 对部分系列失败仍返回成功，刷新编排器可能把陈旧快照当成完整结果（confirmed）。

### 多级 SPEC partial 写入覆盖原有型号和值（P0，confirmed）

`overseas/scenarios.py:1070-1080` 在 `model_ok < model_expected` 时仍调用 `db.save_spec_sheet(sheet, week, replace_week=False)`。此时 `sheet` 只由成功型号合并而成，失败型号已经不在 `sheet.models` 中；`overseas/db.py:361-365` 又无条件执行 `models=excluded.models`，一次 partial 重抓就会把系列的完整型号清单缩短为成功子集。即使当前周还没有旧 `spec_row`，`spec_export._collect()` 也会按这份缩短后的清单出列，原本成功但本次暂时失败的型号不再出现在导出和 API 中。

同一周已有完整快照时，`overseas/db.py:382-385` 对冲突行无条件用 `values_json=excluded.values_json` 替换整张值映射；成功型号的 JSON 会覆盖旧的失败型号值。`replace_week=False` 只避免了 DELETE，并没有实现方法文档所说的旧值保护。

修复应把 partial 结果与规范快照分开：要么只写状态/错误而不更新 `spec_series` 和 `spec_row`，要么在数据库层按型号合并 `models` 与 `values_json`，并保留期望的失败型号列。成功完成整系列时才允许替换本周快照；同时为“已有完整快照 + 一个型号失败”加回归测试。

### SPEC 批量写入失败时可能提交删除和半成品（P1，confirmed）

完整 SPEC 使用 `replace_week=True`，`overseas/db.py:371-388` 先 DELETE 同周旧行，再批量 INSERT，方法没有显式事务回滚。若中途写入抛错，`spec_crawl` 异常路径会继续调用 `db.log_error()` 和 `record_spec_series_status()`；这些方法各自 `commit()`，而 `Database.close()` 在 `overseas/db.py:49-53` 也会无条件 commit。因此失败系列可能提交“旧快照已删、只写入部分新行”的状态，审计虽显示 failed，数据却已经缺行。

修复应把整次 sheet 写入包在显式事务中，异常时 rollback；`Database.close()` 在未成功完成的事务上应 rollback 而不是 commit。状态审计应在数据事务成功或回滚后单独落盘，避免用记录错误的 commit 间接提交半成品。

### 评价分页的瞬时失败被当成完整成功（P1，confirmed）

在 `scripts/crawl_kakaku_reviews.py:275-310`，只要第一页解析出非空评价就把 `review_ok` 设为 true。若下一页 HTTP/网络错误，代码只设置 `review_transient` 并退出翻页；因为 `review_ok` 仍为 true，`:313-374` 不会进入クチコミ回退。最终只要 `collected` 非空，`:375-384` 直接返回 `status="ok"`，没有把 `review_transient` 传到 `ModelResult`，因此 `save_to_db()` 不会写瞬时失败的 `crawl_error`，型号熔断计数还会被重置。

BBS 列表或主题页已经收集到部分帖子后发生同样故障时，`bbs_transient`/`thread_transient` 也会被忽略。结果文件和数据库看起来成功，但缺少后续页；问题在于“部分数据 + 未完成遍历”的完成判定，不是 URL/指纹去重本身。

修复应区分 `had_items` 与 `complete`：瞬时失败时至少返回带 `transient` 的 partial/failed 状态并保留已收集数据，同时写错误审计、触发有限的型号/品牌熔断；若策略要求继续兜底，则合并クチコミ结果后仍不能把未完成的レビュー翻页标成完整 `ok`。状态枚举和 API 展示需要能表达 partial。

### 解析异常被误归类为瞬时失败并触发品牌熔断（P1，confirmed）

`scripts/crawl_kakaku_reviews.py:592-598` 的主循环对 `crawl_model()` 捕获所有 `Exception`，统一构造 `transient=True` 的 `ModelResult`。选择器/解析器 bug、数据格式错误等确定性故障会被伪装成网络故障；连续三次后 `:612-629` 直接跳过剩余型号，并在入库审计中按 transient 记录。已有的 `_is_transient_exception()` 没有用于这条总兜底路径。

修复应使用同一失败分类器：只有 timeout、connection、browser/Playwright 等可识别瞬时异常才设置 transient，其余标为 parse/failed 并重置连续瞬时计数，避免解析器改版把整个品牌错误熔断。

### API 任务数据库路径与服务查询路径分叉（P1，confirmed）

`overseas/api/server.py:381-388` 把服务查询数据库设置为 `SETTINGS["db"]`，但 `overseas/api/jobs.py:126-159` 的 `_spec_cmd`、`_price_cmd`、`_review_cmd` 都使用模块配置的 `config.DB_PATH`；`_spec_refresh_cmd` 更完全没有传 `--db`，会退回环境变量或项目默认路径。用 `python -m overseas.api.server --db X` 启动后，通过 `/api/jobs` 触发的任务可能成功写入 Y，而 `/api/status`、导出和健康统计继续读 X，看起来像数据库状态没有落盘。

修复应让 JobManager 在服务启动时接收运行时 DB 路径，并把同一个显式路径传给所有支持 `--db` 的脚本（尤其是 `refresh_spec.py`）；不要依赖导入时的全局配置。应增加 API 使用非默认临时 DB 提交任务后，查询同一 DB 能看到 `crawl_run`/状态的集成测试。

### 硬超时/取消不闭合 `crawl_run`，且树终止不可靠（P1，confirmed）

`overseas/api/jobs.py:334-352` 在硬超时后只更新内存中的 `Job`，直接终止采集子进程；被终止的 CLI/脚本没有机会执行各自的 `db.finish_run()`（例如 `scripts/crawl_kakaku_reviews.py:643-651`、`overseas/scenarios.py:874-899` 的正常收尾），所以对应 `crawl_run` 会永久保持 `running`，未执行的系列/型号也没有阈值跳过审计。API 取消路径同样只改 Job 状态，不能闭合数据库运行记录。

`overseas/api/jobs.py:89-119` 的 `_terminate_process_tree()` 在 `proc.terminate()` 后只要父进程及时退出就立即 return，Windows 的 `taskkill /T /F` 和 Linux 的子进程处理都不会执行；`scripts/refresh_spec.py:42-47` 的 `subprocess.run(timeout=...)` 也只终止直接子进程。浏览器孙进程因而可能残留，硬超时的“进程树已终止”消息与实际不符。取消还有竞态：若进程在 `proc.poll()` 已非空时才收到取消请求，函数返回后仍把 Job 标为 cancelled，即使子进程已经以 0 成功退出。

修复应为任务建立可追踪的 run/job 关联，在父进程终止前或终止后只把该 run 标记为 stopped/failed，并记录 timeout/cancel 的 `crawl_error`；数据库更新要带明确 run_id，不能按“最近 running”猜测。Windows 使用 Job Object（或在父进程仍存活时可靠的进程树方案），Linux 用新进程组并杀进程组；取消前重新检查退出码，已结束的任务不要改成 cancelled。

### S4 详情页评价回退失败静默完成（P1，confirmed）

通用适配器默认 `reviews_url()` 返回空串，S4 因此走 `overseas/scenarios.py:449-461` 的详情页回退。若 `collect_detail()` 返回 `payload=None`、被拦截或得到空评价，分支没有增加 `stats.fail`、没有 `db.log_error()`，随后直接退出该 SKU；运行最后仍在 `:493-495` 以 completed 结束。该 SKU 的评价缺失既没有在审计中体现，也不会使 CLI/API 报失败。

修复应按 `res.blocked`、瞬时 HTTP/网络失败、解析空结果分别记录错误；成功拿到详情但确实没有评价可以记录明确的 no_reviews 状态，失败则增加 fail 并保留回退 URL/原因。

### interval 定时任务会重复入队，重启后又停止调度（P1，confirmed）

`overseas/api/jobs.py:553-559` 触发任务后把 `last_run_at` 写成带 `+00:00` 的 `_now()`，再用本地无时区的 `now` 调 `_compute_next()`；`overseas/api/jobs.py:501-508` 比较 aware 与 naive datetime 会抛 `TypeError`。异常被 `:559` 的宽泛 `except` 吞掉，任务已经入队但 `next_run_at` 没保存，30 秒后同一个 schedule 仍然 due，会不断重复入队。该异常已用当前代码直接调用 `_compute_next` 复现。

此外 `_load()` 在 `overseas/api/jobs.py:421-429` 构造 Schedule 时没有读取持久化的 `next_run_at`，所以 API 重启后所有已保存 schedule 的下一次时间为空，永远不会触发。修复应统一使用 UTC aware 或统一本地 naive 时间，并在加载时恢复/重算 `next_run_at`；入队和状态保存应具备幂等保护。

### SPEC 部分失败仍可能让刷新命令返回成功（P2，confirmed）

`overseas/cli.py:191-192` 只检查 `st.ok` 和 `st.stopped`；一个品牌只要有一个系列成功、没有触发品牌熔断，即使 `stats.fail > 0` 也返回 0。`scripts/refresh_spec.py:124-141` 因而继续导出并把该品牌视为成功，XLSX 只要能从旧快照生成有效表头和数据就可能通过校验，最终 `:159-169` 打印整体 OK。连续失败的审计行虽会写入状态表，但调度器/CI 的退出码不能阻止不完整交付。

修复应把 partial failure 作为默认非零结果，另提供显式 `--allow-partial`（与“允许未翻译”分开）；刷新仍可继续其他品牌并导出状态，但最终成功必须要求选定品牌没有失败/空系列，或明确返回 partial。
