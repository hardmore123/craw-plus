## 一、要解决的问题

每接入一个电视品牌官网，都要手写一份 Python 适配器,里面写死了入口 URL、分页方式、
型号链接正则、规格表选择器、反爬策略。实测规模：

| 站点 | 手写行数 |
|---|---|
| samsung_mx | 502 |
| samsung_us | 376 |
| tcl_us | 374 |
| lg_ca | 277 |
| philips_ca | 224 |

一个新站从 0 到可用要写并调几百行代码，**这是当前人工成本的主要来源**。

目标：把"接一个新站"从**写代码**降级为**给一个 URL + 审一份配置**，
日常重跑零人工、零 LLM 调用。

---

## 二、核心思路：一条契约把"判断"和"执行"分开

```
        判断（每站不同，需要智能）          执行（固定，可复用）
    ┌──────────────────────────┐      ┌──────────────────────────┐
    │  这站产品链接选择器是啥？   │      │                          │
    │  分页是哪种方式？          │ ──►  │   generic_spec 引擎       │
    │  规格藏在 JSON 还是表格？   │      │   按配置抓全站            │
    └──────────────────────────┘      └──────────────────────────┘
                    │                              ▲
                    └──── AdapterSpec (JSON) ──────┘
                              唯一契约
```

**关键设计**：判断的产物是**配置**，不是代码。

这一条决定了整个系统的安全性与可维护性：
- 坏配置最多抓不到，不会执行失控逻辑
- 引擎能力固定，能力边界可枚举、可校验
- 判断可以由人做、由 LLM 做、由智能体做——**执行端完全不变**

## 三、四段流水线 + 双入口

```
                ┌──────── 入口 A：skill（人机协同，判断力优先）────────┐
                │        .kiro/skills/spec-schema-gen/                │
                └────────────────────┬───────────────────────────────┘
                                     │
   Probe ───────► Generate ───────► Verify ───────► Execute
   探测结构        产出 schema        双层校验        引擎抓全站
   spec_probe     智能体 / LLM       静态 + 实测      generic_spec
                                     │
                ┌────────────────────┴───────────────────────────────┐
                │  入口 B：程序化 CLI（无人值守，可进定时任务）         │
                │        overseas.cli spec-onboard                    │
                └────────────────────────────────────────────────────┘

   日常重跑：读已存 schema → 引擎全量抓 → 导出（完全不调 LLM）
```

### 为什么是双入口，不是二选一

这是本轮论证得出的核心结论：

**skill 替换的是 Generate 这一环，而当前挡住覆盖面的缺口全在 Execute 端。**

| | 上限由谁决定 |
|---|---|
| 能自动化多少站 | **引擎能力档位**（Execute） |
| 接一站要多久、能不能诊断出难点 | **判断力**（Generate） |

所以：
- 想扩覆盖面 → 必须扩引擎（P0 任务），skill 化帮不上
- 想提高逐站诊断效率 → skill 化收益明显
- 想要改版自愈、无人值守 → 必须保留程序化入口（skill 需人开 IDE）

两个入口**共用**同一份 schema 格式、同一套校验、同一个引擎。

## 四、四条不可动摇的原则

| 原则 | 落地方式 | 防什么 |
|---|---|---|
| **只产配置，不产代码** | 需执行 JS 只能引用已登记片段库 | 失控逻辑 |
| **审计表即 reward 函数** | 用真实入库数据打分，不看自述 | 闭环自我感觉良好 |
| **找全率硬否决** | `expected.model_count` 对比，< 80% 直接判失败 | ★**抓了一半当成功** |
| **能力边界显式化** | 白名单常量；越界报错而非静默降级 | 假装支持导致隐性缺失 |

> 第三条是红线。**误判成功比抓不到更危险**——抓不到会被发现，
> 抓了一半标成功会污染交付数据且难被察觉。

### 防脱节机制

文档最大的风险是**代码改了文档没改**，导致智能体照旧文档写出跑不通的 schema。
所以有自动检查：

```powershell
py -3.12 .kiro/skills/spec-schema-gen/selfcheck.py
```

它会核对：引擎三个白名单常量是否都在 schema 规范里有记录、规范文档里的示例
是否真能过 `validate_spec`、已转正 schema 是否仍合法、cases 里 `verdict` 与找全率
是否自相矛盾、文档有无死链。

**改动引擎或 skill 后请跑一次。** 它上线第一次就抓出了一处过度声明
（某站标 success 但找全率只有 80%）。

## 九、一句话总结

用一份 JSON 契约把"每站不同的判断"和"固定的抓取执行"分开；
判断可由智能体或程序化 LLM 产出，执行端不变；
**覆盖面靠扩引擎档位，效率靠 skill 的判断力，安全靠找全率硬否决与只产配置不产代码。**
