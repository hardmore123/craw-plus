## 一、结论摘要

### 一句话结论

> 本期交付的不只是几批数据，而是**一套"用配置而不是代码接站、用真实数据而不是自我感觉验收、
> 把红线写成可执行校验"的采集方法**——接一个新站的代码量从 **224~502 行降到 0 行**，
> 日常重跑 LLM 成本降到 **0**，且**接站成本会随接站数量递减**。

### 三个核心结论

| # | 结论 | 支撑数字 |
|---|---|---|
| **1** | **接站从"软件开发"变成了"配置审核"** | 代码量 224~502 行 → **0 行**；耗时 1~3 天 → 目标 ≤2 小时 |
| **2** | **探索一次、长期复用，经验还能沉淀** | 日常重跑 **token = 0**；同型站第二次接几乎零成本 |
| **3** | **规模化瓶颈已不在代码，而在网络线路与合规** | 服务器出海实测 **3/14** 站可达；18 个北美零售站仅跑通 5 站 |

## 二、背景与目标

### 2.1 起点问题

业务需要持续获取各国电视产品的**规格、价格、口碑**数据。这类工作的固有难点是：

> **目标站点结构无穷多，而每接一个新站都要重新做一遍判断。**

改造前是**手写适配器**：每个品牌官网写一份代码，写死入口 URL、分页方式、
型号正则、规格选择器、反爬策略。

| 站点 | 手写行数 |
|---|---:|
| samsung_mx | 502 |
| samsung_us | 376 |
| tcl_us | 374 |
| lg_ca | 277 |
| philips_ca | 224 |

**基线：一个新站从 0 到可用要写并调几百行代码，1~3 天。**
成本主要不在"敲代码"，而在**"每个站都要把它的结构重新判断一遍"**。

### 2.2 目标

| 目标 | 验收口径 |
|---|---|
| 把"接新站"从写代码降级为审配置 | 新站代码量 **0 行** |
| 日常重跑零人工、零 LLM | 每次全量抓取 **token = 0** |
| 数据可信、可交付 | 找全率 **≥95%**；匹配准确率 **100%**；守恒率 **100%** |
| 可无人值守 | 定时任务 + 断点续跑 + 审计留痕 |

## 三、核心方法：一个"越用越强"的闭环

> 这是本期最具复用价值的产出，也是把成本从"线性"变成"递减"的关键。

### 3.1 闭环结构

```
        每个新站只做一次                每天 / 每周自动跑
    ┌──────────────────────┐     ┌──────────────────────┐
    │  ① 探索              │     │  ② 复用              │
    │  智能体 + 技能库      │     │  引擎读配置           │
    │  判断结构、产出配置   │     │  固定代码抓全站       │
    └──────────┬───────────┘     └──────────┬───────────┘
               │                            │
               ▼                            ▼
        schema / adapter ────────► 爬取结果 + 审计数据
               ▲                            │
    ┌──────────┴───────────┐                │
    │  ③ 经验回灌          │◄───────────────┘
    │  案例库 / 经验库 / 套路│
    │  → 下次遇同型站几乎零成本│
    └──────────────────────┘
```

### 3.2 三个环节的定位

| 环节 | 谁来做 | 频率 | 成本 |
|---|---|---|---|
| **① 探索生成** | 智能体 + 技能库（人审把关） | 每个新站**一次** | 一次性模型成本 + 人工审核 |
| **② 复用爬取** | 固定引擎读配置 | 每天 / 每周 | **零模型成本、零人工** |
| **③ 经验回灌** | 强制沉淀（做成流程机制） | 每次接站后 | 几分钟 |

**一句话**：把"每个站都要写代码"变成
「**每个站只探索一次，之后永远复用，而且每探索一次下次更快**」。

### 3.3 与改造前对比

| 维度 | 改造前（手写适配器） | 改造后（闭环） |
|---|---|---|
| 新站代码量 | 224~502 行 | **0 行（纯配置）** |
| 新站接入耗时 | 1~3 天 | 目标 ≤2 小时 |
| 日常重跑模型成本 | — | **0（已达成）** |
| **第二次遇同型站** | 还是 1~3 天 | **查案例库命中，通常 1 轮就过** |
| 站点改版 | 改代码 + 重新部署 | **改配置，不发版** |
| 能力边界 | 静默降级、假装支持 | **显式化，越界报错** |
| 故障可追溯 | 靠人回忆 | **审计表 + 案例库留痕** |

### 3.4 四条不可动摇的原则（保证闭环长期可控）

| 原则 | 落地方式 | 防什么 |
|---|---|---|
| **只产配置，不产代码** | 需执行的脚本只能引用**已登记片段库**，禁止内联 | 失控逻辑，且**无代码执行面** |
| **用真实数据当验收依据** | 拿**真实入库结果**打分，不采信模型/脚本自述 | 闭环"自我感觉良好" |
| **红线要能自动否决** | 找全率与预期对比，**< 80% 直接判失败** | ★**抓了一半当成功** |
| **能力边界显式化** | 白名单常量；越界**报错**而非静默降级 | 隐性数据缺失 |

> **第三条是红线**：误判成功比抓不到更危险——
> 抓不到会被发现；抓了一半标成功会污染交付数据，且很难被察觉。

### 3.5 第三个环节是关键差异点

前两个环节（探索生成、复用爬取）行业里已有人做；
**真正让成本递减的是第三个环节——经验回灌**。

它的落地方式是**强制流程**，而不是"建议"：

```
探索前：先查案例库（按域名 / 建站特征 / URL 路径匹配相似站）→ 命中就直接套
结束后：强制回写一条案例 + 更新经验库 / 结构型套路（成功失败都要写）
```

配套**自检机制**防止"经验腐化"：核对结论标记与找全率是否自相矛盾、
规范文档与代码白名单是否脱节、已定稿配置是否仍合法。
（上线第一次即抓出一处**过度声明**：某站标"成功"但实际找全率仅 80%。）

## 五、能力边界：能做什么、不能做什么

> 主动讲清边界，比宣称"全自动"更有价值——**它直接决定排期和预期**。

### 5.1 已能解决的问题（按类别）

| 类别 | 能解决 | 解决思路 |
|---|---|---|
| **页面结构** | 静态列表 / 滚动懒加载 / 点加载更多 / 编号页码 / **替换式渲染** / 参数分页 / JS 延迟渲染 / 多尺寸变体 / 规格藏在接口里 | 先分类再解决；滚动"等到不增长"；优先找站点**权威来源** |
| **反爬与访问** | 轻中度自动化检测 / 需登录态 / 拦截误判 / 限流 429+410 / 登录墙误判 | 真实浏览器通道 + 真实用户 profile；拦截标记分"明确/歧义"；站级熔断 |
| **数据正确性** | 选择器改版 / 同名覆盖 / 型号错配 / 尺寸错配 / 配件价当主价 / 隐蔽丢数 / 误判成功 | 规则外置 + 兜底链；内部唯一键；分级匹配 + 尺寸守卫；祖先链校验；守恒校验；找全率硬否决 |
| **长任务运维** | 超时被 kill / 中途失败 / 部分成功当全量 / 死循环 / 看不到进度 | 后台跑；幂等设计 + 断点续跑；统一终止条件；用产物文件判断进度 |
| **AI 协作** | 接站写代码 / token 成本 / 模型幻觉 / 不收敛 / 提示注入 / 经验流失 | 只产配置；把模型移出运行期；静态+实测双层校验；轮次上限；强制回灌 |

### 5.2 明确不能解决的

| 类别 | 做不到 | 原因 |
|---|---|---|
| **网络** | 强挑战（Cloudflare 等）、IP 层封锁、验证码 | 参数补不出来；**登录、UA、Cookie 全无效，唯一变量是出口线路**（实测：真实浏览器带 cookie 仍被拦） |
| **业务** | 需登录才显示的价格、加购后显示的价格 | 业务规则与账号权限，不是技术问题；按"不自动处理"记录，不用别的字段硬凑 |
| **站点策略** | 平台服务端硬上限 | 例：某站评价每型号只给 8 条，已穷尽 9 种途径 |
| **能力** | 型号无规律 / 带签名接口 / 特殊分页累积抓取 / 需点 tab 展开的 SPA | 需要人工补一块；**如实报告缺口，而不是假装全自动** |
| **运维** | 同一 profile 并发、会话过期自动续期 | 用户目录是独占资源；不存账号密码（也不该存） |

### 5.3 止损标准（已有明确判据）

```
型号无规律无法用正则框住 / "加载更多"通用点击点不开 /
需要多级页面才拿到型号 / 需要带签名的接口 /
需要登录或验证码或加购后才显示
  → 停止，记为「需人工适配」并说明缺口
```

### 5.4 诚实的能力定位

> 系统的真实价值是：
> **标准站全自动；特殊结构站自动识别 + 复用已有能力，
> 无匹配时精确告知人工补哪一块**——而不是"任意站零人工"。

## 六、问题与风险

### 6.1 本期已解决的代表性问题

| 问题 | 影响 | 处置 |
|---|---|---|
| **同名系列互相覆盖** | 看着齐了其实少了（入口 64/224，落库仅 60/205） | 引入内部唯一键，迁移 + 补抓 → 全齐 |
| **登录墙被误判为反爬** | 触发站级熔断，**621 个型号静默全跳过**且日志正常 | 两者分开归因，登录失效豁免熔断并提示修复 |
| **配件价被当主价** | 32 吋电视抓到 $9.49，且每次跑都漂移 | 价格区祖先链校验；拿不到判定就保守拒绝 |
| **分页找全率 48%** | 初判为选择器问题，实为脚本转义 bug | 先证伪再改代码，修复后 **48% → 100%** |
| **限流撞墙** | 某站 204 型号撞 148 个限流 | 站级熔断 → **5 个即停** |
| **反爬误判** | 两个正常站被判"被抓不到" | 白名单豁免 → 实测通过 |
| **权限类环境问题** | 服务器无浏览器、装不了运行时 | 离线浏览器 + SSH 隧道，"本地驱动、服务器执行" |

### 6.2 现存风险与阻塞

| 级别 | 风险 | 影响 | 当前处置 |
|---|---|---|---|
| **高** | **出海线路缺失** | 北美零售规模化无法推进（18 站仅跑通 5 站） | 已测清边界，**拿到线路前不做无谓重试** |
| **高** | **抓取合规边界未确认** | 规模化前的风险敞口 | 已做技术兜底（合规准入白名单），**待内部确认** |
| 中 | 生产化四件套未落地 | 影响"无人值守"与改版自愈能力 | 已排 P1 |
| 中 | 规格质量指标未系统测量 | **唯一未测的红线指标**，可能影响已完成的验收结论 | 建议尽早补测 |
| 中 | 代码分支分叉未合并 | 影响交接与后续协作 | 需人工解冲突，**不强推主干** |
| 低 | 多会话并发修改同一工作区 | 可能影响正在跑的全量任务 | 已写入交接文档风险提示 |

## 八、可向其他团队复用的部分

> 以下 8 条不依赖本项目代码，换任何采集类任务都能直接借鉴。

| # | 借鉴点 | 一句话 |
|---|---|---|
| **1** | ★ **把"每个站都做一遍"改成闭环** | 探索一次 → 复用长期 → **经验回灌**；成本随接站数量递减 |
| **2** | ★ **让 AI 产配置，不产代码** | 安全、可审计、可回滚、能力边界可枚举；顺带把模型移出运行期 |
| **3** | ★ **经验必须"强制回写"并且校验** | 写成流程最后一步，成功失败都要写；不校验就会沉淀错误 |
| 4 | **先分类，再解决** | 翻页不是一个问题，是八个问题；先判断类型再选手段 |
| 5 | **等稳定 ≠ 等固定时间** | 懒加载要"连续 N 轮不增长"，不是"滚 3 次" |
| 6 | **红线要能自动否决** | 硬阈值把关；**误判成功比抓不到更危险** |
| 7 | **登录 ≠ 绕过反爬** | IP 层被拦时登录/UA/Cookie 全无效，唯一变量是出口线路 |
| 8 | **长任务要幂等 + 可续跑 + 会停** | 后台跑、唯一约束、统一终止条件、站级熔断 |

### 最后一句

> **把"接一个新站"从写代码降级为审配置；
> 让经验回流成资产，使接站成本随接站数量递减；
> 用真实数据而不是自我感觉来验收；
> 把红线写成可执行的校验。**
